# Maintainability Policy

Human-maintainable code is a hard quality requirement for `ai_orchestrator`.

Why this matters:

- the system is growing quickly across CLI, workflow, schema, and review layers;
- AI-generated code can become technically correct but too abstract or too hard for humans to safely maintain;
- safety gates only help if humans can still understand and review the code that implements them.

Principles:

1. Prefer simple functions over generic frameworks.
2. Add abstractions only after repeated concrete use.
3. Keep CLI thin and move domain logic into focused modules.
4. Keep modules focused on one responsibility.
5. Keep schema and domain models grouped by responsibility.
6. Avoid hidden side effects and surprising write paths.
7. Preserve deterministic behavior in safety and review flows.
8. Tests should verify behavior, not implementation trivia.
9. Refactor after feature bursts instead of normalizing complexity.
10. Human readability beats cleverness.

Relation to AI-generated code:

- AI-assisted changes must remain understandable to a human maintainer who did not generate them.
- Reviewers should prefer the simplest implementation that preserves required behavior and safety.
- Over-engineering, abstraction churn, and hard-to-trace control flow are quality problems even when tests pass.

Scope:

- this policy applies to code generated by `ai_orchestrator`;
- this policy also applies to the `ai_orchestrator` codebase itself.

The goal is not elegance for its own sake. The goal is code that a human can read, review, validate, and safely change later.
